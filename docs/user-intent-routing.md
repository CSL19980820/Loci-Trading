# 用户请求路由表

本文件把“客户说了什么，该怎么做”固定下来，避免执行时发散。

## 1. 典型请求与标准动作

| 用户说法 | 标准动作 | 不允许的动作 |
|---|---|---|
| “分析这只股票” | 先跑程序取数，再让 Codex 在线核验，最后输出定稿 | 直接口头下结论，不产出报告 |
| “给我 PDF” | 必须实际生成 PDF 文件 | 只给 HTML 或口头说“可以导 PDF” |
| “先读项目，用项目规则分析” | 严格按 `analyze.py + 模板 + online evidence` 执行 | 脱离项目自己随便写一段分析 |
| “没数据也先出一版” | 只能走 `--evidence-only` 证据版 | 伪造当前价、K 线或技术指标 |
| “这个样式不行，重做” | 优先修 HTML/PDF 渲染层和封面图 | 只改 Markdown 文案不改最终样式 |
| “帮我判断是否值得买入” | 只能输出条件成熟度、风险点和待核验信息 | 输出确定性买入建议 |

## 2. 请求关键词映射

### 2.1 数据请求

关键词：

- `分析`
- `看一下`
- `值得买吗`
- `持仓`
- `买入`
- `回本`

动作：

- 先运行程序取数
- 再决定完整版或证据版

### 2.2 输出请求

关键词：

- `PDF`
- `定稿`
- `模板`
- `封面`
- `样式`

动作：

- 先检查 `assets/report-cover.png`
- 再检查 HTML/PDF 渲染层
- 最后验证真实 PDF 是否生成

### 2.3 协作请求

关键词：

- `配合 Codex`
- `在线预览`
- `网页核验`
- `公告`

动作：

- 读取 `summary.json` / `ai_context.json`
- 生成 `online_evidence.json`
- 合并到定稿模板

## 3. 出错时的优先级

### 3.1 数据失败

优先动作：

1. 尝试备用源
2. 如果仍失败，默认中止
3. 只有用户明确接受证据版，才走 `--evidence-only`

### 3.2 PDF 失败

优先动作：

1. 检查 `wkhtmltopdf`
2. 检查 HTML 是否结构化
3. 重新导出 PDF

不允许：

- PDF 没生成还说“已经出了 PDF”

### 3.3 模板失败

优先动作：

1. 修模板空值处理
2. 保持章节结构不变
3. 重新生成

不允许：

- 临时删章节
- 改成自由发挥式输出

## 4. 默认响应纪律

- 有真实数据：出完整版
- 无真实数据：默认失败
- 明确接受证据版：出证据版
- 要 PDF：必须产出真实 PDF 文件
- 要按项目来：必须回到项目 CLI、模板和证据链，不允许脱离项目聊天式回答
