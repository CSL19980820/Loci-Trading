2026-09-17 14:20 正式轮次的持仓报价全部有效；六次基础查询全部成功，预取耗时 5.043 秒。随后模型第一逻辑轮次没有保存任何正文/推理增量或完整回复，研究阶段超过原 270 秒总期限，未落账。

此前输入减负和按需取证仍在生效；故障直接表现为请求连接未得到完整回复。原恢复逻辑将网络断开错误地当作流式协议不可用，重发了非流式请求，而单次网络等待又可以占用整轮剩余预算，导致恢复机会不足。

Clash 当前 active、NRestarts=0，没有查到该时段相关 journal 错误；这些信息不能排除节点或远端线路瞬时故障。事后同模型小请求 1.973 秒完成，也不能倒推出 14:20 时链路正常。客户端证据不足以进一步区分 B.AI 网关、模型上游或代理远端链路。

## 修复范围

- 仅 Guardian 将单次网络超时配置为 `min(90秒, 本轮剩余期限)`。这是网络等待超时，不是把完整研究或持续输出的推理限制为 90 秒；原 270 秒研究总期限和 300 秒执行边界保留。
- 对尚未发出正文或推理增量的网络传输失败，最多重新发送一次当前**流式**模型请求；不重启整个 Agent，不重复之前已执行的工具，不更换模型、供应商、思考配置、消息、工具定义或输出预算。
- 已有正文/推理、取消或总期限到期，不走重试。第二次仍失败时明确失败，不进入第三次非流式盲等。
- 原本确实不支持流式的其他错误保留既有兼容回退。新网络恢复选项默认关闭，由 Guardian 显式启用；其他 Agent 调用方没有自动改变行为。
- 运行记录新增 `model_retry` 时序，保存原因、传输错误类型和尝试编号。未获得上游 usage 的失败请求无法确认实际 token 用量，不能把本地零计数等同于上游未处理或未计费。

这里没有缩短参考池、删除持仓合同、裁剪模型研究，或提高交易容差来避开失败；也不能保证外部服务持续故障时依旧完成交易。

## 首有效响应的独立期限

前一版的 90 秒属于网络操作超时，不是首有效响应的墙钟期限；SSE 心跳可持续刷新网络读取等待。此次在交易员启用恢复的请求中增加独立的 90 秒首响应期限，从发起调用开始计时，包括等待响应头。响应头、心跳、角色空增量和用量信息均不算有效响应；正文、原生思考和工具调用增量才结束首响应等待。总研究期限仍为 270 秒，后续持续流式读取也受剩余总期限约束。

传输使用已安装的 httpx2.AsyncClient 和 asyncio 取消等待，通过同一调用线程的 Runner 驱动；事件和 SQLite 检查仍在原线程执行。超时取消当前 I/O 并关闭响应，不遗留继续运行的请求线程。首响应超时作为 FirstResponseTimeout 进入已有一次流式重试；已有任何有效增量则不重试，避免重放部分工具响应。非交易员未启用选项时保留原传输路径。

时间线新增 response_headers、first_stream_line、first_semantic、first_response_timeout/request_deadline 及请求内耗时，区分通道建立与模型实际输出。该诊断不保存密钥或推理正文。

本地验证：26 项首响应/恢复/交易员按需研究测试与 90 项 Agent/流式回归测试通过，两组不重叠。真实本地 HTTP 服务覆盖未返回响应头、持续心跳、仅角色增量、正文/思考/工具流超过首响应期限、总期限中断，以及超时后完全相同的流式请求恢复；原恢复测试覆盖已执行工具不重跑、部分响应不重试、取消和持续失败。
