# 选股编排与数据范围架构复审

## 范围与结论

本轮检查异步选股、通用选股用例、行情快照和热库选择的职责边界。
保留现有 DDD 模块化单体；数据范围与指标预热由计算用例定义，编排层负责日期循环、进度及入库。
发现并修复两处数据范围问题，未声称完成全仓审计或全市场容量验证。

## 已修复

### 编排层预取全库证据，绕过计算范围

`screen_run.py` 曾调用不带参数的 `store.data_snapshot()`，再给区间各日传同一个快照。
该方法调用 `source_evidence`，没有证券与日期条件时会读取全库关联回执。
它既不能证明区间运行期间数据库被冻结，也会把实际计算范围之外的来源证据带入结果。

现在逐日调用通用 `screen`，在解析当日股票池及指标预热窗口后，由该用例带
`codes + start + end` 取得证据。删除了编排层的无范围预取和快照覆盖。
区间多日会执行多次有界取证，本次未量化整段区间的时间收益。

### 热库健康不等于覆盖历史计算窗口

原检查只回答热库是否覆盖近期窗口、是否跟上全量库末日。
用户查询更早的历史日时，即使当天存在，也可能缺少指标预热所需历史。

现在读取热库前，使用与通用选股一致的 `signal_history_bars`，核对首个目标日
预热起点至区间末日的全部交易日；缺少历史、预热不足、区间中间缺日均回退全量库。
显式要求全历史的策略仍直接使用全量库。

### 计算容量与进程边界统一

针对本记录原先指出的「Job 有闸门、HTTP/助手没有」问题，选股面板加载前现在统一
经过 `src.shared.screen_capacity`：`job:screen`、异步/同步 HTTP 选股和 AI
`strategy_screen` 共用进程级 FIFO 许可。同步 HTTP 与 AI 在容量满时快速返回 429/工具
错误，异步 HTTP 与 Job 使用可取消的排队；租户只影响标签与任务归属，不绕过全局内存闸门。

`compare` / `optimize` 的大面板计算默认进入受控 `spawn` worker；单次回测 Job 可显式
使用相同边界。worker 只接收显式行情库路径和租户标识，父任务负责取消、超时、RSS
取样和终态收口，结果回显执行模式与 worker PID。这样复用了 TSP 值得借鉴的进程隔离
与资源观测思路，同时没有复制第二套成交引擎。

本次新增入口回归与全仓回归均通过；本段改动尚未部署线上，生产并发容量仍需按真实宿主
资源做压测后再调整槽数。

## 仍待处理的架构缺口

1. **版本标签不等于冻结读事务。** 当前逐日快照描述取证时观察到的版本；没有承诺
   数据来源取证与面板加载期间的数据库内容绝不变化。强复现应沿用研究冻结机制，
   或在有界任务中评估统一读事务及其 WAL 保留成本。
2. **其他历史入口仍需对齐。** 本次热库范围修复覆盖异步区间选股；其他选股/助手入口
   的历史日期支持应逐个核对，不能把本次结果外推成所有入口已统一。

回滚使用前版镜像 `loci-qianlong:2.0.0-20260909-120300`，按 `deploy/README.md` 操作。
本轮未 commit/push；没有访问已搁置的便携版。
